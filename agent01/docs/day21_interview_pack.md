# Day21｜简历、3 分钟口述与面试演练

## 1. 项目名称与一句话

**Enterprise Knowledge Agent｜企业知识库智能问答与文档分析系统**

基于 RAG 与有限工具调用的企业文档问答系统，支持 PDF/DOCX/TXT 入库、知识库隔离、多轮问答、可追溯引用、固定集评测与容器化编排。

- 使用 FastAPI、SQLAlchemy 2、MySQL、Chroma、Redis 与 Streamlit 构建分层单体，覆盖上传入库任务、文档生命周期、会话持久化、版本化缓存、Bearer 身份映射、所有者授权、限流与结构化脱敏日志。

## 3. 三分钟项目口述稿

### 0:00–0:30｜业务问题

这个项目解决的是企业内部文档分散、关键词搜索不理解语义，以及通用大模型回答时不能证明“依据哪份内部文档”的问题。我希望做的不只是一个聊天页面，而是一条能隔离知识库、拒绝无证据问题、返回真实来源、可以评测和复现的工程链路。

### 0:30–1:25｜架构与数据流

系统前端用 Streamlit，后端是 FastAPI 分层单体。用户上传 PDF、DOCX 或 TXT 后，服务会校验类型和大小、净化文件名、计算内容哈希，再用后台任务解析、清洗和切分，调用 Embedding 后把 Chunk 和元数据写入 Chroma。MySQL 保存知识库、文档状态、任务、会话和消息，Redis 只做带知识库与索引版本的可失效缓存。

问答时先校验 Bearer 身份和知识库所有者，读取有限历史，把追问改写成独立问题，再按 `knowledge_base_id` 强制过滤检索。模型看到的是带编号的受约束证据，最终文件名、页码和 `chunk_id` 由服务端用真实检索元数据回填，避免模型伪造来源。

### 1:25–2:05｜关键取舍与难点

我没有做开放式 Agent，而是保留确定性 RAG，并只增加检索、单文档总结、双文档对比三个白名单工具。路由只选择意图，工具执行层仍做参数 schema、文档状态和权限二次校验，并限制步数、超时、总预算和证据大小。这样牺牲了部分通用性，但更容易解释、测试和审计。

另一个难点是缓存和删除一致性。缓存键不能只有问题，还要包含知识库、索引版本和检索配置；文档入库、删除或重建会推进知识库版本，从而避免旧答案跨版本命中。

### 2:05–2:40｜指标与证据

我把评测集版本化为 50 题，Dev 和 Holdout 各 25 题，覆盖事实、数字边界、列表、跨段落、精确术语、追问和 10 个信息不足问题。指定 DeepSeek Chat 和 text-embedding-v4 的保存响应重放平均 1.98 分，49/50 获 2 分；事实覆盖、一致、相关、拒答和引用正确率在这个固定集上都是 100%。工程侧还有 160 项测试和 12/12 的 Agent 路由回归。所有数字都带数据集、模型、Prompt 和参数版本，不把离线哈希向量指标包装成生产质量。

### 2:40–3:00｜局限与下一步

当前局限是 OCR、生产级可靠任务队列、精细 RBAC、多实例限流、规模化稀疏索引和压测监控还没有完成；本机真实容器验收、持久化、备份与覆盖恢复已通过，但这仍不等于生产部署。下一步优先做可靠任务队列和权限审计，再根据失败集校准信息不足阈值，而不是继续堆 Agent 工具。

## 4. STAR：最难的工程问题

**Situation**：系统既要支持多知识库和多轮问答，又要避免串库、缓存旧答案和模型伪造引用。

**Task**：建立一条可测试、可审计的证据链，让权限、检索、缓存和来源在同一个知识库版本上保持一致。

**Action**：在服务层统一校验所有者；检索强制 `knowledge_base_id` 过滤；缓存键加入知识库和索引版本；入库、删除、重建时更新版本；模型只能引用内部来源 ID，响应阶段再映射真实文件、页码和 Chunk；用跨用户、跨知识库、缓存失效、Prompt Injection 和引用回归覆盖关键边界。

**Result**：160 项测试通过；固定 Agent 路由 12/12；50 题保存响应重放平均 1.98/2，拒答与引用正确率均为 100%。同时保留限制：该结果来自合成固定集，不能推导到开放域或生产流量。

## 5. 模拟面试第一轮：RAG 与评测

### 1. 请完整描述一次问答的数据流。

身份和知识库权限校验后，服务读取有限历史并改写追问，查询版本化缓存；未命中时生成查询向量，按知识库过滤 Chroma Top-K，必要时做融合或词法重排，把编号证据放入受约束 Prompt。模型返回答案和来源编号，服务端映射真实文件、页码与 `chunk_id`，保存会话后返回。

### 2. 为什么不能把整份文档直接放进上下文？

成本、延迟和窗口不可控，长文本容易忽略关键证据，也难做知识库权限过滤和来源追踪。RAG 先缩小证据范围，并让召回和生成可以分别评测。

### 3. Chunk 500、Overlap 50 是怎么来的？

它是当前固定评测配置，不是通用最优值。选择时平衡语义完整性、召回粒度、重复内容和 Token 成本；调整只能在 Dev 上比较，Holdout 不用于反向调参。

### 4. Top-K 越大越好吗？

不是。K 太小会漏召回，太大会引入噪声和额外 Token。当前检索评测看 Recall@K、MRR 和信息不足准确率，回答评测再看事实、拒答和引用，不能只优化一个指标。

### 5. 为什么真实检索的 Hybrid/Rerank 没有直接设为默认？

它们把 MRR 从 Vector 的 90% 提高到 96.25%/97.50%，但信息不足准确率从 10% 降到 0%。排序收益伴随拒答边界恶化，因此默认选择必须看端到端质量和阈值校准，而不是只看召回排名。

### 6. 引用如何避免伪造？

检索结果先获得内部来源 ID，模型只允许引用这些 ID。后端再用已检索元数据回填文件名、页码和 Chunk；未知 ID 会被拒绝或忽略，模型不能直接决定真实来源。

### 7. 如何判断信息不足？

结合距离过滤、证据覆盖和生成拒答约束。检索空结果与回答拒答是两个不同层次；阈值需要按文档类型和失败集校准，不能把某个分数当成绝对真理。

### 8. 50 题够吗？

足够建立开发期回归，但不足以代表生产分布。优势是数据版本、Dev/Holdout、期望事实和来源都可追踪；下一步应扩大真实匿名场景、增加困难负例和人工复核一致性，而不是夸大当前结论。

### 9. 为什么不用 LLM-as-judge？

当前优先可重复的事实、禁止事实、拒答和引用规则。LLM Judge 可补充语义判断，但必须保存 judge 模型、Prompt、原始理由，且不能覆盖事实矛盾或无效引用等确定性失败。

### 10. 1.98/2 是否意味着已经没有问题？

不意味着。它只证明指定数据集、模型、Prompt 和参数下的保存响应质量；仍有一个 1 分样例，且重放不能证明今天的外部模型状态，也不能代表开放域、OCR 文档或真实企业流量。

## 6. 模拟面试第二轮：工程、安全与 Agent

### 11. 为什么是分层单体而不是微服务？

当前主要目标是边界清晰、低部署成本和端到端可调试。真正出现独立扩缩容、故障隔离或团队所有权边界后再拆分，避免过早引入分布式事务和运维复杂度。

### 12. MySQL、Chroma、Redis 分别保存什么？

MySQL 保存业务关系和状态；Chroma 保存 Chunk 向量与检索元数据；Redis 保存可失效缓存。上传原件单独在持久卷，便于重新入库。Redis 丢失不应影响正确性。

### 13. 缓存键为什么不能只有问题？

同一问题在不同知识库、索引版本、用户权限、检索模式、模型或 Prompt 下结果不同。当前设计至少绑定知识库和版本，并配置 TTL/失效；否则容易串库或返回删除文档前的旧答案。

### 14. 如何防止越权和资源枚举？

Bearer Token 映射明确用户；服务层统一校验知识库所有者；文档、任务、会话、Chat 和 Agent 都复用授权；检索再次强制知识库过滤。对不存在和无权限资源统一返回 404，减少枚举信息。

### 15. Prompt Injection 怎么处理？

证据被标记为不可信数据，文档不能改变系统规则；程序侧再做认证授权、知识库过滤、工具白名单、参数 schema、步数/超时、输出结构和注入回归。只能说分层缓解，不能说彻底解决。

### 16. 为什么需要 Agent？

它只用于在问答、整篇总结和两文档对比之间选择受控工具。普通知识问答仍走确定性 RAG，避免为了“Agent 化”而把稳定路径变成无限循环。

### 17. Agent 如何防止失控？

固定三工具白名单、Pydantic 参数、权限透传、同库限制、最多 2 步、单工具 15 秒、总预算 25 秒、证据大小上限、安全轨迹和失败即停。同步 SDK 的底层调用不能强制取消，这是现有限制。

### 18. 后台入库任务可靠吗？

演示版使用 FastAPI `BackgroundTasks`，能返回任务状态，但进程崩溃后的恢复、持久化重试、幂等调度和多实例消费并不完整。生产化应迁移到可靠队列，并增加租约、重试、死信和可观测性。

### 19. Docker 做了哪些安全处理？

多阶段构建、固定 uv 版本、`uv sync --locked`、运行镜像不保留构建工具、非 root UID 10001、只读根文件系统、移除 capabilities、`no-new-privileges`、受控 tmpfs、MySQL/Redis 不暴露宿主端口、日志轮转和资源/PID 限制。

### 20. 你如何证明部署可用？

当前证据包括 Docker Desktop 4.88.1 的真实镜像构建、四服务 healthy、Alembic head、两次主链路、`down/up` 持久化、日志脱敏抽查、三类备份校验及覆盖恢复复验；远端 clean-clone 还以隔离镜像/端口/卷完成无缓存构建、健康、安全、持久化和 160 项离线回归。它证明本机可复现运行，不等于生产部署或生产 SLO。
